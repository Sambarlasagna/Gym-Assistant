01Project Overview

Personalized Gym Assistant is a role-based, client-side web application designed to streamline gym management for both gym members and administrators. Members can view personalized workout plans, diet plans, and announcements. Admins can create and manage those plans and publish updates — all from a browser, with no backend server required.

The application is built on a hybrid tech stack: Vanilla HTML/CSS/JavaScript handles navigation, authentication, and dashboards; a React + Vite bundle powers the interactive workout and diet plan interfaces. All state is persisted in localStorage.

RoleKey Capabilities
MemberLogin → Dashboard → View Workout Plans → View Diet Plans → Read Announcements
AdminLogin → Admin Dashboard → Create/Edit Plans → Post Announcements

02Design Principles Applied

Four core software design principles were consciously applied throughout the codebase.

🔲

Abstraction

Complex behaviours are hidden behind clean interfaces. Users of a function or class do not need to know how it works — only what it does.

  • GymManagementApp class in assets/app.js abstracts all routing and auth-guard logic behind a single object.
  • DIET_PLANS and WORKOUT_PLANS constant objects abstract raw data; UI code loops over them without knowing internal structure.
🧩

Modularity

The system is split into independent, self-contained modules. Each module owns its HTML, CSS, and JS.

  • auth/ — login & signup only
  • member-dashboard/ — member view only
  • admin/ — admin panel only
  • workout-diet/ — workout & diet pages
  • react-app/ — React components (separate build)
🎯

Cohesion

Each module and function does one thing well — all its code is closely related to a single responsibility.

  • diet.js contains only diet-related logic: data, create, edit, delete, render.
  • member-dashboard.js contains only member view logic.
  • announcements.js handles only announcement CRUD — nothing else.
🔗

Low Coupling

Modules communicate through events or shared data — never through direct function calls across module boundaries.

  • Navigation uses a custom event bus: CustomEvent('navigate', ...)
  • React bundle reads/writes localStorage — fully decoupled from vanilla JS.
  • Auth and dashboard pages share data only via localStorage keys.

Code Evidence — Abstraction & Low Coupling

// assets/app.js — GymManagementApp class
// Abstraction: all routing logic hidden inside handleNavigation()
class GymManagementApp {
    handleNavigation(page) {
        const routes = {
            'dashboard':      '../member-dashboard/dashboard.html',
            'manage-diet':   '../workout-diet/manage-diet.html',

03High-Level Architecture

Architectural Style: Client-Side MVC-Lite + Component Layer

The application follows a "Client-Side MVC-Lite" pattern — a simplified Model-View-Controller approach adapted for a zero-backend, localStorage-driven environment. A separate React Component Layer handles the most interactive UI sections.

MVC RoleMaps toFiles
ModelBrowser localStorage JSON storeslocalStorage keys: currentUser, dietPlans, workoutPlans, announcements
ViewHTML pages + dynamically generated DOM + React componentsauth/*.html, member-dashboard/*.html, admin/*.html, react-app/src/
ControllerGymManagementApp class + per-module JS filesassets/app.js, diet.js, workout.js, admin-dashboard.js

Architecture Diagram

Why This Architectural Style?

  • No backend needed: localStorage provides sufficient persistence for a demo/learning project.
  • Role separation: The Auth Layer enforces role-based access at the routing level — clean and centralized.
  • Hybrid rendering: Static HTML for fast page loads; React for richer, interactive data UIs.
  • Docker + Nginx enables production-like deployment of a static site.

Data Flow

User Action → HTML Page → JS Controller → Read/Write localStorage → DOM Update / Redirect Auth: login.html → auth JS → localStorage.setItem('currentUser') → redirect to dashboard Admin: manage-diet.html → diet.js → localStorage('dietPlans') → page reload React: workouts.html → React bundle → localStorage('workoutPlans') → component re-render

04User Interface Design

The UI follows a consistent design language: a dark navy navbar (#0c2435) with clay-orange accents (#d96c2f) and a warm sandy background (#f6f1e9). This palette is energetic and professional — appropriate for a fitness application.

UI Design Choices for User-Friendliness

  • Role-based navigation: Members see only their links; Admins see only their links — no confusion.
  • Card-based layout: Information grouped into cards with clear headings for easy scanning.
  • Color-coded importance: Red/yellow borders instantly communicate announcement urgency.
  • Tab/filter controls: Goal-based filtering lets members find relevant plans without scrolling.
  • Admin-only controls: Create/Edit/Delete rendered only when isAdminUser() is true.

05Design Decisions & Rationale

  • Decision 1

    Hybrid Vanilla JS + React Architecture

    What: Core pages use plain Vanilla JS. Workout and Diet plan pages use React + Vite compiled components.

    Why: Vanilla JS requires zero build tooling and loads instantly — perfect for simple CRUD pages. React shines for the data-heavy, filterable plan UIs. This hybrid avoids over-engineering simple pages while getting React's power where it genuinely helps.

  • Decision 2

    localStorage as the Sole Data Store

    What: All user data, plans, and announcements are stored in localStorage as JSON. No backend, no database, no API calls.

    Why: Makes the app fully portable — runs from file://, GitHub Pages, or Docker with zero server dependency. For a learning/demo project, a backend would be disproportionate. The trade-off (device-local data) is acceptable and documented.

  • Decision 3

    Centralized Role-Based Routing in app.js

    What: The GymManagementApp class is the single controller for all route guards and navigation. Modules fire CustomEvent('navigate') — they never redirect themselves.

    Why: A single routing controller means access control is enforced in exactly one place. Adding a new protected route requires one line change in app.js — not changes scattered across many files.

  • Decision 4

    Module-per-Feature Folder Structure

    What: The repository is organized into feature-based folders: auth/, member-dashboard/, admin/, workout-diet/, react-app/.

    Why: This structure scales — developers find everything related to the admin panel inside admin/ without searching the whole repo. New features can be added as new folders without modifying existing ones (Open/Closed Principle).

  • Decision 5

    Docker + Nginx for Deployment

    What: A Dockerfile wraps static files in an Nginx container. docker run -p 8080:80 gym-assistant serves the full app.

    Why: Containerization ensures identical behavior on any machine regardless of OS or local tooling. It prepares the project for real-world deployment patterns (cloud VMs, CI/CD). Nginx serves static assets with correct MIME types and efficient caching headers.

06Maintainability & Future Extensibility

The design was intentionally structured to allow the following extensions without modifying existing working code:
Future FeatureHow current design supports it
Add a real backend/databaseReplace localStorage read/write in module JS files with API calls — UI layer does not change
Add a new member feature (e.g., Progress Tracker)Create new progress/ folder, add entry to routes in app.js — zero changes to other modules
Add hashed password authAuth logic is isolated in auth/ — replace the check in one place
Replace Vanilla JS pages with ReactThe CustomEvent navigation contract stays the same — React components just fire the same navigate events
Multi-language (i18n) supportAll display strings are in HTML templates/JS template literals — extracting to a language object is straightforward
